# Архитектура

Сервис «AI-дизайнер презентаций» (кейс 14, VK Tech; команда DesignFactor) —
монолит на FastAPI: один процесс, один asyncio-таск на задачу, без очередей и
БД. Frontend — один статический `frontend/index.html` (десктоп), который
ходит в API того же домена (в проде — через nginx-прокси).

Документы рядом: [README.md](README.md) — установка, переменные окружения,
ограничения; [MODELS.md](MODELS.md) — модели и скиллы; [AUDIT.md](AUDIT.md) —
проверки аудита и тесты.


## Слои пайплайна и их границы

Пайплайн разбит на пять слоёв. Каждый слой получает и отдаёт явный артефакт
(файл в `storage/outputs/<job>/` или pydantic-модель), и только через него
соседние слои знают друг о друге — это позволяет заменять слой (другую LLM,
другой рендер) и проверять слои по отдельности.

| Слой | Модули | Вход | Выход | Что знает / чего не знает |
| --- | --- | --- | --- | --- |
| **1. Парсинг** | `pipeline/parser.py`, `pptx_template_parser_generator/`, `pipeline/template_engine.build_template_json`, `pipeline/sample_slides.py`, `pipeline/design_system.py` | `.pptx`-шаблон | `DesignManifest` (палитра, гарнитуры, стили таблиц/графиков), Template JSON (`template.json`: макеты, слоты, каталог, композиции-образцы, `design_source`), `DesignSystem` для интерфейса | Детерминированный, без моделей. Ничего не знает о брифе и содержании. |
| **2. Генерация содержания** | `pipeline/content_agent.py` (скилл `content_planning`), `pipeline/dramaturgy.structure_content` (скилл `content_structuring`), `pipeline/excel_import.py` | бриф, назначение, диапазон слайдов, данные из Excel | `ContentPlan` (`content_plan.json`): слайды с назначением, тезисами, графиками, таблицами; `structured.json`: тезисы `{head, text}`, метрики `{value, label}`, подзаголовки, выводы | Работает только со смыслом: не знает про макеты, слоты, шрифты. Единственный слой с LLM в основном потоке. |
| **3. Вёрстка** | `pipeline/dramaturgy.py` (`slide_intent`, `select_compositions`, `build_variant_plan`), `pipeline/template_engine.py`, `pipeline/slide_clone.py`, `pipeline/library.py`, `pipeline/styling.py` | Template JSON + `structured.json` + `ContentPlan` | `plan_variant_{a,b,c}.json` и `variant_{a,b,c}.pptx` | Детерминированный (одинаковый вход → одинаковая колода). Выбирает композиции под роль слайда и профиль плотности, клонирует образцы, строит нативные графики/таблицы, подгоняет текст. Не меняет смысл текста. |
| **4. Аудит** | `pipeline/audit.py` (детерминированные проверки + VLM по скиллу `visual_audit`), `pipeline/audit_fix.py` (скилл `audit_text_fix`), `pipeline/audit_overlay.py` | `.pptx` выбранного варианта, `DesignManifest`, PNG-превью | `Job.audit_issues[variant]` (`AuditIssue` с `code`, `shape_id`, `bbox`, `fixable`), исправленный `.pptx` | Не знает, как слайд собирался: проверяет готовый файл по чек-листу Приложения 1. Точечные исправления правят фигуры на месте. |
| **5. Экспорт** | `pipeline/export.py`, `pipeline/preview.py`, `pipeline/soffice.py` | `.pptx` варианта | `pptx` / `pdf` / автономный `html`, PNG-превью | LibreOffice под глобальным замком, изолированный профиль на запуск. |

Оркестратор (`app/orchestrator.py`) — единственное место, где слои
соединяются; API (`app/api/routes.py`) лишь транслирует HTTP в вызовы
оркестратора. Промпты и параметры всех LLM/VLM-шагов лежат отдельными файлами
(`backend/skills/*.yaml`, `pptx_template_parser_generator/prompts/*.txt`) —
см. раздел «Промпты и конфигурация как файлы».

## Схема потока

```
                       ┌────────────────────────────────────────────────────────────┐
  .pptx-шаблон ───────▶│ 1. ПАРСИНГ                                                 │
                       │  parser.parse_template   ──▶ DesignManifest (палитра,      │
                       │                               шрифты, стили таблиц/графиков)│
                       │  template_engine.build_template_json ──▶ Template JSON     │
                       │     (движок pptx_template_parser_generator + обогащение:   │
                       │      типографика слотов, роли фактоидов, тема шрифтов)     │
                       └──────────────┬─────────────────────────────────────────────┘
                                      │  design-system (для UI)  ◀── design_system.build_design_system
  бриф + назначение ─┐                ▼
  + доп. пожелания   │ ┌────────────────────────────────────────────────────────────┐
                     └▶│ 2. ПЛАНИРОВАНИЕ  (последовательно: контент ▶ макеты)       │
                       │  content_agent.generate_content_plan ─▶ ContentPlan        │
                       │     (структура: обложка / цифры / разделы / финал,         │
                       │      тезисы, графики, таблицы; промпт skills/*.yaml)       │
                       │  template_engine.planner_brief(ContentPlan) ─▶ бриф с      │
                       │     пронумерованной структурой и подсказками типа слайда   │
                       │  template_engine.plan_presentation  ─▶ layout_plan.json    │
                       │     (планировщик коллеги: outline ▶ copy ▶ fill ▶ repair,  │
                       │      промпты pptx_template_parser_generator/prompts/*.txt) │
                       │  ⇒ слайд N ContentPlan == слайд N layout_plan: графики и   │
                       │    таблицы попадают на «свои» слайды                       │
                       └──────────────┬─────────────────────────────────────────────┘
                                      ▼
                       ┌────────────────────────────────────────────────────────────┐
                       │ 3. СБОРКА ТРЁХ ВАРИАНТОВ (в thread-pool, по одному)        │
                       │  derive_variant_plan(A|B|C) ─▶ supplement_plan_text        │
                       │   ─▶ fill_image_slots ─▶ render_variant                    │
                       │   (scripts.generate.create_presentation + нативные         │
                       │    графики/таблицы python-pptx в слоты макета)             │
                       │  ─▶ storage/outputs/<job>/variant_{a,b,c}.pptx             │
                       │  A/B — без разделителей, C — с разделителями (длиннее)     │
                       └──────────────┬─────────────────────────────────────────────┘
                                      ▼  awaiting_variant_choice
                       ┌────────────────────────────────────────────────────────────┐
                       │ 4. ВЫБОР ВАРИАНТА  (пользователь; превью через soffice→png) │
                       └──────────────┬─────────────────────────────────────────────┘
                                      ▼  awaiting_audit_choice
                       ┌────────────────────────────────────────────────────────────┐
                       │ 5. АУДИТ (опционально)                                     │
                       │  audit.audit_presentation — детерминированные проверки     │
                       │  audit.audit_content_with_vlm — 11 вопросов к VLM          │
                       │  POST /fix — пересборка + повторный аудит                  │
                       └──────────────┬─────────────────────────────────────────────┘
                                      ▼  done
                       ┌────────────────────────────────────────────────────────────┐
                       │ 6. ЭКСПОРТ  pptx | pdf (soffice) | html (автономное        │
                       │    слайдшоу: PDF ▶ PNG ▶ data-URI, клавиатура/обзор)       │
                       └────────────────────────────────────────────────────────────┘
```

Статусы `Job`: `queued → parsing → planning → assembling → awaiting_variant_choice
→ awaiting_audit_choice → auditing → done | failed`
(`app/schemas/job.py`, оркестратор — `app/orchestrator.py`).

## Движок шаблона (`pptx_template_parser_generator`)

Общий с командой движок разбирает `.pptx` в **Template JSON** и умеет собирать
презентацию по плану так, что макеты, фоны, декор и медиатека шаблона
воспроизводятся один в один (`scripts/generate.py::create_presentation`).

Ключевые поля Template JSON:

- `variants[]` — каждый макет шаблона: `layout_name`, `layout_file`, `slots{}`
  (позиция, `semantic_role`, `resolved_font` — гарнитура/кегль/жирность/цвет),
  `generation_contract.text_slots[]` с ограничениями по символам и строкам;
- `variant_catalog[]` — «витрина» макетов для планировщика: `family`,
  `visual_variant`, `narrative_role` (cover/section/content/closing/…),
  `content_pattern`, `composition` (`title_body`, `parallel_content`,
  `text_with_media`, `image_caption_pair`, …), `best_for`, слоты текста и
  изображений;
- `theme_fonts` (major/minor), `source_mode` (`layouts` — макеты взяты из
  layout-XML, либо `slides` — из слайдов-примеров).

Backend дополняет Template JSON (`template_engine.build_template_json`):

1. `_enrich_slot_typography` — для каждого слота вычисляет фактический шрифт
   (слот → placeholder мастера → тема), чтобы дизайн-система и аудит видели
   реальную шкалу кеглей;
2. `_fix_metric_roles` — внутри макета слоты `metric_*` делятся на
   `metric_value` (крупный кегль, ≥ 2× минимального в группе) и `metric_label`;
   без этого планировщик писал число в подпись и наоборот;
3. `relaxed_template` — для планировщика «рекомендуемый» бюджет символов
   поднимается до максимального (иначе заголовки обрезались до 17 символов при
   допустимых 25); максимум остаётся жёстким ограничением валидатора.


## Откуда берётся дизайн: макеты, образцы, библиотека

Шаблоны устроены по-разному, и парсер это учитывает (`sample_slides.detect_design_source`):

| `design_source` | Признак | Что используем |
| --- | --- | --- |
| `layouts` | в макетах есть плейсхолдеры тела, слайды-образцы пустые или их нет | макеты шаблона (классический путь) |
| `slides` | макеты почти пустые (только заголовок), дизайн живёт на слайдах-примерах | клонирование слайдов-образцов (`slide_clone`) |
| `mixed` | и то и другое | и макеты, и образцы — выбирает драматургия |
| `library` | ни примеров, ни макетов с телом | собственная библиотека компоновок на «чистом» макете шаблона (`library`) |

Библиотека подмешивается и к шаблонам с образцами — только недостающие виды
(`build_library_variants(only_kinds=…)`): таблица, график и крупный тезис, если
их нет среди образцов; разделитель, если его не дают ни образцы, ни макеты;
«Ключевые цифры», если образцы метрик вмещают меньше трёх значений; «Текст»,
«Карточки» и «Две колонки», если ни один макет шаблона не имеет тела и среди
образцов нет текстовых/карточных композиций (VK WorkSpace: все макеты —
«Титульный слайд» и «Заголовок»; без этого слайд с 2–4 тезисами получал
«только заголовок»). При подборе композиции библиотека — запасной вариант:
если у шаблона есть образец, совместимый с назначением слайда, библиотечная
компоновка получает штраф (`dramaturgy._score`), кроме видов без замены
(график, таблица, метрики, разделитель), которых среди образцов нет. Образец на
«титульном» макете с таблицей или графиком считается слайдом данных, а не
обложкой. Базовый макет
выбирается по «чистоте» (`pick_base_layout`): декор макета и фоновой картинки
(водяные знаки «03 04», контуры плашек, в том числе полупрозрачные — оценка
`template_engine._picture_busyness`) штрафуется, а если фон ровный, но с
бледными плашками, под контент подкладывается плашка цвета фона (`bg_cover`).
Макеты с плейсхолдером за границей слайда в каталог не попадают.

Каждый слайд-образец разбирается на **композицию**: заголовок, повторяемые
блоки (серии одинаковых фигур; серии с одним количеством и одной сеткой
склеиваются в блоки «иконка + заголовок + текст»), одиночные слоты (тело,
заметка, подпись, контакты, метрика-«герой»), таблицы, графики, картинки.
Блоки, объединённые в одну большую группу, разбираются на детей с пересчётом
геометрии. Вид композиции — обложка, оглавление, карточки, проблемы, метрики,
таймлайн, таблица, график, тезис, текст, финал; схемы со стрелками, команда
(фото людей) и галереи распознаются, но под произвольный контент не
подставляются.

При рендере по образцу (`slide_clone.render_sample_slide`):

- `adapt_units` подгоняет число блоков под тезисы: лишние убираются (ряд из
  одной строки — растянуть или расставить равномерно), недостающие
  достраиваются клонированием последнего блока с пересчётом сетки (ряды,
  колонки, масштаб не ниже 0,55 × 0,6; «сирота» в последнем ряду штрафуется);
- 7 тезисов на сетку из 6: без настойчивого требования пользователя план
  урезается до 6, при «строго 7» — макет достраивается;
- заголовок не залезает на декор (зоны исключения по фигурам слайда и макета),
  расширяется до свободной ширины и уменьшает кегль под место до следующей
  фигуры; числа-метрики в заголовках карточек укрупняются;
- незаполненные плашки-заметки/теги удаляются вместе с подложкой, любой
  незаполненный текст образца очищается, лишние абзацы удаляются;
- нативные таблицы и графики вставляются на место образцовых, картинки — в
  образцовые фото-слоты (только в насыщенном варианте);
- одинаковые плашки с разным собственным текстом (6 карточек-примеров) — одна
  серия, а не пары «заголовок + текст»: 3 тезиса займут 3 карточки, а не 3 из
  6; «лестница» (каждый блок в своём ряду и колонке) читается слева направо и
  не перестраивается — под неё берётся ровно её число блоков;
- макет шаблона с фиксированным числом плашек (6 карточек) под другое число
  тезисов штрафуется сильно (`+3 + 1/блок`): плашки макета со слайда убрать
  нельзя, и вместо трёх пустых карточек выбирается текстовый макет или образец;
- заголовок карточки без пояснения (лаконичный вариант) укрупняется до 1,35×,
  если хватает места до следующей фигуры.

Графики (`styling.style_chart`) стилизуются под фон слайда
(`background_luminance`: заливка слайда → макета → мастера, картинка на весь
слайд — по средней яркости): на тёмном фоне подписи осей, легенда и подписи
данных светлые, сетка приглушённая; подписи значений включены всегда — жирные,
на 2 pt крупнее легенды; легенда снизу и только при двух и более сериях; на
линейном графике — маркеры в узлах.

Слайд-раздел не остаётся «голым»: `slide_intent` собирает заголовки следующих
слайдов до следующего раздела (`section_inside`, ≤ 4), `structure_content`
просит у модели содержательный лид раздела, и разделитель получает лид + список
пунктов (в тело/подзаголовок) либо карточки-обзор с этими пунктами; композиции
раздела без единого текстового слота штрафуются (`+2.0`).

## Три варианта: ось различия

Для шаблонов с `design_source` ≠ `layouts` (и для `layouts`, если структура
удалась) три варианта различаются **плотностью подачи и длиной колоды**
(`dramaturgy.DENSITY_PROFILES`), а не типом макета:

| Вариант | Профиль | Блоков на слайд | Текст блока | Слайды-разделители |
| --- | --- | --- | --- | --- |
| A · Лаконичный | заголовки тезисов, короткие подписи; для выступления со спикером | до 4 | только заголовок | нет — самая короткая колода |
| B · Сбалансированный | заголовок + короткое пояснение | до 6 | ≈110 символов | нет |
| C · Насыщенный | развёрнутые пояснения, заметки-выводы, фото в предусмотренных слотах; для чтения без спикера | до 8 | ≈170 символов | да — смысловые части открываются разделителями, колода длиннее |

### Разделители и длина колоды

Контент-агент (`skills/content_planning.yaml`) ставит слайды-разделители
только в колодах от 9 слайдов и только перед частями из двух и более слайдов;
разделитель несёт лид части (одно предложение). Дальше `dramaturgy.dropped_slides`
решает, что из плана попадёт в вариант: A и B собираются **без**
разделителей, C — **с** ними (разделитель, открывающий меньше двух слайдов,
убирается и в C — он лишь повторял бы заголовок соседа). Так три варианта
дают колоды разной длины (например, 9 / 9 / 11 слайдов), что и было целью:
вариативность не только в плотности, но и в структуре.

Чтобы графики, таблицы и правки не «съезжали» при разной длине, у каждого
слайда варианта хранится `source_index` — номер слайда в плане содержания;
`template_engine._visual_objects` берёт данные графиков/таблиц по нему, а
`Job.variant_sources` отдаёт соответствие в интерфейс. На этом же строится
режим сравнения «слайд за слайдом» (по слайду плана, с заглушкой «в этом
варианте разделителя нет — колода короче») и действие «Взять из варианта X»
(недоступно, если в варианте-источнике этого слайда нет).

`structure_content` один раз (чанками по 8 слайдов) просит LLM разложить
каждый слайд ContentPlan на тезисы `{head, text}`, метрики `{value, label}`,
подзаголовок и вывод — дальше все три варианта собираются детерминированно.
`select_compositions` выбирает композицию под намерение слайда
(`slide_intent`) с глобальным скорингом: соответствие числа блоков, метрик,
наличие таблицы/графика, штрафы за повторы и за «дальние» виды композиции.

Чтобы варианты отличались не только плотностью, у каждого профиля есть
**характер** (`prefer`/`avoid` по видам композиций: A — тезисы, метрики,
воздух; B — карточки, колонки, таймлайны; C — фото, текст с пояснениями,
таблицы), **ротация** равнозначных образцов (детерминированный сдвиг по хэшу
id композиции) и **взаимное различие**: B детерминированно пересчитывает
выбор A, C — выбор A и B, и на том же слайде композиция, уже взятая другим
вариантом, стоит дороже на 1,2 (`avoid`). Обложки, разделители, финалы и
компоновки тезисов поэтому у трёх вариантов разные, если шаблон даёт выбор.
Если структурирование или сборка по драматургии падает, вариант собирается по
старому пути ниже.

### Классический путь (макеты шаблона)

Все три варианта собираются из **макетов загруженного шаблона** по одному и
тому же плану содержания; различие — в выборе макетов и подаче контента
(`VARIANT_STRATEGIES` в `template_engine.py`).

| Вариант | Контентные слайды | Обложка / раздел / финал | Графики и таблицы |
| --- | --- | --- | --- |
| A · Классический | одноколоночные макеты `title_body` | первая визуальная версия семейства (`visual_index = 0`) | в нижней части текстовой зоны |
| B · Структурный | двухколоночные `parallel_content` (только симметричные колонки), тезисы делятся на две колонки | вторая версия (`visual_index = 1`) | в правой колонке |
| C · Визуальный | макеты с изображением `text_with_media` / `image_caption_pair`, фактоиды; необязательные фото-слоты заполняются из медиатеки шаблона | третья версия (`visual_index = 2`) | в текстовой зоне |

Если семейство обложек/разделителей имеет меньше версий, чем нужно, индекс
берётся по модулю. Слайды с особыми паттернами (`person_profile`, `quote`,
`metrics`, `section_transition`, `introduction`, `call_to_action`) сохраняют
макет планировщика во всех вариантах — это несущие элементы повествования.

`supplement_plan_text` — страховка от полупустых слайдов: если планировщик
выбрал макет только с заголовком или оставил текстовый слот пустым, слот
заполняется тезисами соответствующего слайда из `ContentPlan` с учётом бюджета
символов/строк слота.

`fill_image_slots` — обязательные слоты изображений заполняются картинками из
медиатеки шаблона (по тому же макету, где они лежали), финальный слайд с QR
получает QR-код на контакты (`segno`), при отсутствии подходящих медиа —
запасное изображение из шаблона.


## Доработка слайдов после сборки

`orchestrator.edit_slide(job, variant, index, action, source)` пересобирает
один слайд выбранного варианта без полной перегенерации:

- `recompose` — `dramaturgy.select_compositions(..., exclude=…)` с историей
  уже показанных композиций для этого слайда (`job.slide_edits`); когда
  альтернативы исчерпаны, история сбрасывается;
- `rewrite` — `dramaturgy.restructure_slide(...)`: LLM переформулирует один
  слайд (заголовок, тезисы, подписи) при той же структуре данных, результат
  записывается в `structured.json`;
- `take_from` — слайд с тем же `source_index` (номером в плане содержания)
  копируется из `plan_{source}.json`; если в варианте-источнике такого слайда
  нет (он собран без разделителей), возвращается понятная ошибка.

После правки план варианта сохраняется, `render_variant` перезаписывает тот же
`.pptx` (кэш превью инвалидируется по mtime), замечания аудита по варианту
сбрасываются, а если аудит уже проводился — задача получает `audit_stale=True`
до повторного `POST /jobs/{id}/audit`.

## Дизайн-система (для интерфейса)

`GET /templates/{id}/design-system` возвращает `DesignSystem`:

- `colors` — палитра темы + фактические цвета фигур;
- `fonts`, `theme_fonts` — гарнитуры и major/minor тема;
- `typography_scale[]` — шкала стилей текста, собранная из реальных слотов
  шаблона: роль (`title`, `subtitle`, `body`, `column_body`, `metric_value`,
  `metric_label`, `caption`, `footer`, `speaker_name`, …), гарнитура, кегли,
  жирность, цвета, число макетов, где стиль встречается;
- `template_layouts[]` — карточки всех макетов шаблона с миниатюрой
  (позиции элементов в %, тип элемента, фон), группировкой по роли
  (Обложка / Раздел / Контент / Финал) и композицией;
- совместимость: старые поля `layouts`, `table_style`, `chart_style`
  из `DesignManifest` сохранены.


## Промпты и конфигурация как файлы

Требование кейса: промпты и конфиги скиллов/агентов лежат в репозитории
отдельными файлами и не зашиты в код. Загрузчик — `app/skills.py`
(`load_skill(name)` читает `SKILLS_DIR/<name>.yaml`, кэширует, падает с
`SkillNotFound`, если файла нет — сервис не стартует с «половиной» промптов).

| Файл | Кто использует | Что внутри |
| --- | --- | --- |
| `backend/skills/content_planning.yaml` | `content_agent.generate_content_plan` | системный промпт контент-стратега, шаблон пользовательского запроса, `response_schema`, `temperature`, `model_name` |
| `backend/skills/content_structuring.yaml` | `dramaturgy.structure_content`, `dramaturgy.restructure_slide` | промпт редактора (тезисы head/text, метрики, подзаголовки, лид раздела), `rewrite_hint` для кнопки «Переписать», `temperature`, `rewrite_temperature`, `chunk_slides` |
| `backend/skills/audit_text_fix.yaml` | `audit_fix` (`bullet_too_long`, `too_many_bullets`) | промпты сокращения и объединения тезисов, лимиты слов/пунктов |
| `backend/skills/visual_audit.yaml` | `audit.audit_content_with_vlm` | системный промпт VLM, 11 вопросов (`key` + `text`), `skip_for_structural` |
| `pptx_template_parser_generator/prompts/*.txt` | планировщик макетов движка (`outline` → `copy` → `fill` → `repair`) | `outline_system`, `outline_repair_system`, `copy_system`, `fill_system`, `repair_system` |
| `backend/app/config/layout_patterns.yaml` | старый движок паттернов (`/fix`, совместимость) | паттерны вёрстки |
| `backend/.env` | `app/config.py` | адреса, модели и ключи LLM/VLM, таймауты, каталоги |

Изменение промпта = правка yaml и перезапуск процесса; версия скилла
(`version`) пишется в файле и попадает в документацию.

## Подгонка текста при рендере (`template_engine.render_variant`)

Детерминированные шаги после заполнения макета, до валидации:

1. `_glue_short_words_in_titles` — предлоги/союзы в заголовках приклеиваются
   к следующему слову неразрывным пробелом (не висят в конце строки).
2. `_clip_to_decor` — если справа от текстового бокса на макете лежит
   декоративная картинка/фигура (паттерн обложки VK), бокс сужается до неё:
   в шаблоне бокс уходит под паттерн, и длинный заголовок иначе прячется.
3. `_fit_slide_text` — shrink-to-fit: кегль уменьшается (не ниже 55 %), если
   самое длинное слово не помещается в строку или заголовок (жадный перенос
   по словам, 1.2 кегля на строку) выше доступной высоты — от верха бокса до
   ближайшей фигуры ниже (`_available_height`). Шрифт и цвет не меняются.
4. Заголовки не режутся до обрубка: лимит слота ×2.2, при усечении
   отбрасываются хвостовые короткие слова («…интеграцию в»).
5. `supplement_plan_text` — если текст планировщика заметно беднее тезисов
   ContentPlan (короче половины и < 40 % бюджета зоны), зона заполняется
   тезисами ContentPlan.

## Деплой

Production: Ubuntu, `systemd`-сервис `designfactor.service` (uvicorn на
127.0.0.1:8811, venv `backend/venv`), nginx раздаёт `frontend/index.html` и
проксирует API. Внешние зависимости: LibreOffice (`soffice`), шрифты шаблона
(Arial/Play → metric-compatible замены для превью).
