# Генератор заготовок PPTX

Программа читает исходную презентацию и создаёт рядом с ней редактируемую
презентацию-заготовку и JSON с описанием слотов. Исходный файл не меняется.

## Запуск

Требуется Python 3.10+ и зависимости из `requirements.txt`:

```powershell
python -m pip install -r requirements.txt
python -m scripts.generate "sample_templates/VK Tech шаблон 1.pptx"
```

По умолчанию результаты сохраняются в `output/`. При повторном запуске файл
не перезаписывается: создаются версии с суффиксами `_2`, `_3` и т. д. Можно
указать другой путь с помощью `--output` и вывести сведения о слотах через
`--verbose`:

```powershell
python -m scripts.generate "моя презентация.pptx" --output "output/готово.pptx" --verbose
```

JSON создаётся автоматически вместе с PPTX. Если нужен только JSON:

```powershell
python -m scripts.export_json "моя презентация.pptx" --output "output/правила.json"
```

Для первичного выбора макета текстовой моделью можно сохранить компактный
каталог без геометрии, стилей и постоянного оформления:

```powershell
python -m scripts.export_json "моя презентация.pptx" --catalog-only --output "output/каталог.json"
```

План, полученный от модели, можно строго проверить до рендеринга:

```powershell
python -m scripts.validate_plan "моя презентация.pptx" "plan.json" --check-images
```

Валидатор проверяет variant, доступность и редактируемость слотов, обязательные
значения, типы данных, длину и количество строк текста и существование файлов
изображений. Старый permissive-рендерер сохранён для обратной совместимости.
В режиме `source_mode=slides` выбранные authored-slide варианты сохраняются в
порядке плана, остальные удаляются; повтор одного варианта пока запрещён.

После проверки тот же план можно отрендерить в итоговую презентацию:

```powershell
python -m scripts.render_plan "моя презентация.pptx" "plan.json" --output "output/result.pptx" --check-images
```

Готовый пример для третьего VK-шаблона находится в
`examples/vk3_demo_plan.json`.

## Полная приемочная проверка

Одна команда создаёт по три визуально разных варианта для каждого PPTX из
`sample_templates`. В каждой презентации по умолчанию 10 слайдов, то есть
выполняется целевой объём ТЗ 10–15 слайдов:

```powershell
python -m scripts.full_test
```

Для четырёх тестовых шаблонов команда создаёт 12 презентаций и соответствующие
JSON-планы в `output/full_test/`. Итоговый `report.json` проверяет открываемость,
число слайдов, наличие редактируемых объектов, выходы за границы, пустые слайды,
служебные заглушки и время генерации. Число слайдов можно изменить в пределах
ТЗ:

```powershell
python -m scripts.full_test --slides 15
```

Три профиля отличаются выбором макетов, порядком материала и плотностью:
`balanced`, `compact` и `visual`. Для режима `source_mode=slides` используются
только уникальные авторские слайды; для макетов разрешено повторное применение.

Этот прогон не вызывает LLM. Он использует связный синтетический контент про
условный продукт «Нова» и подбирает значение по семантической роли каждого
слота. Заполняются все редактируемые текстовые и графические слоты, включая
необязательные. Короткие поля получают краткие смысловые значения целиком,
без обрезания слов. В `report.json` поле `slot_coverage` отдельно показывает
общее и заполненное число слотов; `missing_editable_slots` должен быть пустым.

## Генерация по брифу через локальную модель

Production-команда работает с любым OpenAI-compatible endpoint: Ollama, vLLM
или внешним API. Промпты находятся отдельно в `prompts/`, модель не получает
координаты и не может придумывать слоты. Пайплайн выполняет два шага: выбирает
макеты по `variant_catalog`, затем заполняет их по `generation_contract`.
Невалидный ответ автоматически отправляется модели на исправление до двух раз.
Если локальная модель всё равно придумывает id макетов, переполняет короткие
поля или возвращает ответ Ollama в `thinking`, код сам нормализует результат по
реальным контрактам. Поэтому слабая модель ухудшает содержание, но не должна
ломать структуру PPTX.

Сначала весь путь можно проверить без модели:

```powershell
.venv\Scripts\python.exe -m scripts.generate_ai_suite `
  "sample_templates/VK Tech шаблон 3.pptx" `
  --brief "Презентация о корпоративном водонагревателе" `
  --slides 10 `
  --mock `
  --output-dir "output/ai_suite_mock"
```

Для Ollama установи подходящую instruct-модель и укажи её точное имя:

```powershell
# Если модели ещё нет. Уже установленная qwen3-vl:4b тоже поддерживается.
ollama pull qwen3:8b

$env:PPTX_LLM_BASE_URL = "http://localhost:11434/v1"
$env:PPTX_LLM_MODEL = "qwen3:8b"

.venv\Scripts\python.exe -m scripts.generate_ai_suite `
  "sample_templates/VK Tech шаблон 3.pptx" `
  --brief "Презентация о корпоративном водонагревателе" `
  --purpose "business" `
  --slides 10 `
  --output-dir "output/water_heater"
```

Результат содержит три колоды (`variant_a/b/c`), а внутри каждой папки:

- `catalog.json` — компактный вход выбора макетов;
- `outline.json` — структура, выбранная моделью;
- `plan.json` — полностью заполненный план;
- `presentation.pptx` — редактируемая презентация;
- `audit.json` — открываемость, число слайдов и покрытие слотов.

Для обязательных картинок можно передать `--image path/to/image.png`. Без этого
пайплайн использует первое подходящее растровое изображение из шаблона, чтобы
текстовая модель не придумывала локальные пути. Генерация новых изображений
остаётся отдельным необязательным text-to-image слоем.

## Откуда берутся заготовки

- **Настроенные образцы:** по одному слайду для каждого макета всех образцов.
  Программа использует исходные макеты, сохраняет оформление, группы и
  логотипы; текстовые слоты получают заглушки, графические заполнители
  остаются пустыми.
- **Стандартные образцы PowerPoint:** по одной заготовке для каждого *исходного
  слайда*. Исходный текст заменяется именами слотов (`title`, `text` и т. д.),
  обычные картинки превращаются в заполнители, доступные для вставки в
  PowerPoint. Картинка на всю площадь слайда сохраняется как фон, например
  рамка на иллюстрации. Это слайды выходной презентации, а не новые макеты
  внутри образца PowerPoint.

Режим выбирается автоматически и записывается в JSON как `source_mode`
(`layouts` или `slides`). Распознавание стандартного образца намеренно
консервативное: при сомнении используется режим макетов. Если слайдов нет,
генерируются макеты даже при стандартном образце.

JSON версии `3.0` разделяет данные на три канонических слоя и при этом сохраняет
старые поля для текущего генератора:

- `observed` — только факты из PPTX: тип placeholder, исходное имя, геометрия,
  стили, исходный текст и постоянное оформление; здесь нет эвристических ролей;
- `inferred` — смысловые выводы о макете и слотах с `confidence`, вариантами,
  доказательствами, отношениями и явной неоднозначностью;
- `generation_contract` — разрешённые поля payload, назначение и ограничения
  редактируемых слотов, обязательность и политика переполнения.

Каждый вариант дополнительно содержит:

- `observed.usage_examples` — статистические признаки реальных слайдов,
  использующих этот layout: объём и типы текста, наличие чисел, процентов,
  ссылок и изображений. Исходный текст в JSON не копируется;
- `inferred.composition` — компактный итог внутреннего геометрического анализа:
  тип композиции, альтернативы и смысловые группы слотов. Полный граф близости
  и выравниваний в JSON не экспортируется;
- `inferred.relations` — только полезные смысловые связи (`caption_of`,
  `source_of`, `label_of`, `author_of`), без низкоуровневого геометрического шума;
- `inferred.usage_summary` — агрегированное фактическое использование макета.

Неопределённость и универсальность разделены явно. `semantic_scope` принимает
значения `specific`, `flexible`, `unknown` или `decorative`. Универсальные
слоты содержат `allowed_content_kinds` и передают выбор следующей модели через
`downstream_choice`; ручной review рекомендуется только для `unknown`, а не для
нормально спроектированных универсальных макетов.

`semantic_role` описывает смысл поля, а `allowed_content_kinds` — физический
формат содержимого (`short_heading`, `paragraph`, `bullets`, `photo` и т. п.).
Примеры связываются со слотами только по placeholder или строгому уникальному
совпадению геометрии. В `inferred.usage_evidence` хранится только свидетельство
применения: один пример записывается как `observed_once` без статистических
обобщений, а `summary` появляется начиная с двух примеров. Эти сведения не
дублируются в `generation_contract` и не являются ограничением генератора.

`variant_catalog` предназначен для двухшаговой работы модели: сначала выбрать
`variant` по кратким возможностям макета, затем прочитать полный
`variants[].generation_contract` только выбранного варианта. Семантически
взаимозаменяемые варианты получают одинаковый `family`, но сохраняют отдельные
`visual_variant`, поэтому следующая модель может управлять визуальным
разнообразием.

Формальная схема находится в `schema/template-v3.schema.json`; выходной JSON
содержит `schema_id` и `schema_file`, чтобы валидатор мог выбрать её без
эвристик.

Дополнительно JSON содержит размеры, цвета, шрифты, варианты,
координаты слотов и ограничения (`constraints`), но и слой подсказок для
модели:

- `model_contract` — точный формат плана для генератора, правила заполнения и
  безопасные действия при неоднозначности или переполнении;
- `variant.semantic` — назначение макета, подходящие сценарии, порядок чтения,
  обязательные/необязательные слоты, связанные группы и общий бюджет текста;
- у каждого слота — `semantic_role`, `content_kind`, `required`, `editable`,
  `role_confidence`, рекомендуемая вместимость и поле генератора (`content` или
  `image_content`);
- `placeholder_type`, геометрия и `template_text` сохраняются как факты из
  PowerPoint, чтобы модель могла проверить эвристику.

Старые поля `slots`, `image_slots`, `background`, `images` и `constraints` не
переименованы, поэтому генератор продолжает читать тот же формат. Оценка
вместимости приблизительная: она помогает выбрать макет до рендеринга, но не
заменяет финальную проверку реальным шрифтом. При низкой уверенности JSON явно
указывает неоднозначные слоты вместо того, чтобы придумывать им назначение.
Поле `semantic.review` отдельно сообщает, когда из одного JSON нельзя надёжно
вывести узкую роль и желательно проверить макет визуально. Во всех остальных
случаях модель может работать только по JSON; изображение слайда не является
обязательным входом.

Для воспроизведения оформления одного JSON недостаточно: нужен исходный PPTX.
Программа пока не пишет содержание по брифу и не генерирует таблицы, диаграммы
или видео; эти ограничения также записаны в `model_contract`. Она не создаёт
новые макеты внутри образца из обычных слайдов.

## Структура проекта

```text
pptx_template_parser_generator/
├── pptx_template_parser/   # библиотека разбора PPTX и нормализации JSON
├── scripts/                # команды generate и export_json
├── tests/                  # автоматические тесты
├── examples/               # ручной пример построения презентации
├── sample_templates/       # входные PPTX для разработки и проверки
├── assets/                 # изображения ручного примера
├── output/                 # результаты запуска, не добавляются в Git
├── requirements.txt
└── README.md
```

Основная логика находится в пакете `pptx_template_parser`. Команды используют
её как библиотеку; поэтому их следует запускать из корня проекта через
`python -m scripts.<имя>`.
